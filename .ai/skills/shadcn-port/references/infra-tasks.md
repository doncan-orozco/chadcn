# Wave 0: the infrastructure the gates depend on

Every parity gate stands on five pieces of shared infrastructure, built once before any component (tasks `_theme`, `_base`, `_icons`, `_harness`, `_primitives` in `dev/port/state.json`, each executed by one `shadcn-port-builder` with an explicit `OWNS` list). In this repository they exist; a change to one of them is a change to every component, so `/shadcn-run` re-runs the acceptance checks below when a wave touches them, and `house_check.rb --static-all` guards their layout.

## `_theme`
What exists: the gem's `app/assets/tailwind/chadcn/{engine.css,theme.css,tokens.css,presets/*.css,vendor/*}` (`theme-contract.md`), `lib/chadcn/theme.rb` (`Chadcn::Theme`, validation, presets, import), `lib/tasks/chadcn.rake` (+ `chadcn_aliases.rake`), the `chadcn--theme` controller (toggles `.dark` only) and the theme panel of the dummy app. The React catalog imports the same theme files through the Vite alias `@host-theme` (`dev/react-shadcn-catalog/src/index.css`: `tailwindcss`, `tw-animate-css`, `@host-theme/theme.css`, `@host-theme/tokens.css` and nothing else; `house_check.rb` fails `G5_CATALOG_CSS` otherwise), and the dummy app points `config.chadcn.theme_dir` at the same directory, so both sides read one theme.
Acceptance: the theme tests of the plain suite pass (`test/chadcn/theme*_test.rb`); `(cd dev/dummy && bin/rails theme:check)` passes; `ruby .claude/scripts/shadcn/theme_sync.rb --check-tokens` passes (every semantic Tailwind class the components use generates CSS from `tokens.css`; radius utilities derive from `--radius`); the dummy app's `bin/rails tailwindcss:build` succeeds; a swatch scenario (`bg-primary text-primary-foreground rounded-md`, `bg-primary/90`, `border-input`) resolves identical computed values in the dummy app and the catalog for `zinc`, `slate` and `zinc-radius0` (G4, `parity_run.mjs --theme`). Presets are regenerated only on purpose (`theme_sync.rb --emit-presets`, from the shadcn colors API).

## `_base`
What exists: `Chadcn::Base < Phlex::HTML` in `lib/chadcn/base.rb`, inherited by every part: `cn` (clsx + tailwind-merge semantics, result cache `CN_CACHE`), `merge_attrs(defaults, attrs)` (deep-merges `data:`/`aria:`, caller wins on conflicts, `class` through `cn`, `data-action` concatenated), `normalize_option(value)` (string/symbol, `-`/`_` tolerant), `render_as_child(child, **slot_attrs, &block)` (Radix Slot merge, see api-mapping.md: its OWN merge, separate from `merge_attrs`, because Slot joins `class` plainly with no tailwind-merge, concatenates `data-action` child-first, unions `data-controller` tokens (slot first), merges `style` slot-then-child and lets the child win everything else; verified against `@radix-ui/react-slot` `mergeProps`), `ids(base)` for aria wiring, and the DX helper generator: `Base.const_added(name)` defines, for every nested class that inherits `Chadcn::Base`, a public instance method named `snake_case(name)` that is exactly `render self.class.const_get(name).new(**attrs), &block`; it raises at class-load time when the name would override a Ruby core or Phlex API method (it MAY shadow a Phlex HTML element such as `header`/`title`: intended and documented). Roots call `yield self`. The verified reference implementation is `.ai/skills/shadcn-port/references/dx-helpers-prototype.rb` (golden case 34): adapt it, do not redesign it.
Acceptance: `test/chadcn/base_test.rb`, `base_merge_attrs_test.rb` and `base_cache_test.rb` pass (helper per nested part, `CheckboxItem` -> `checkbox_item`, output identical to the explicit `render Root::Part.new`, `attrs` and block forwarded, a colliding Ruby/Phlex-API name raises, an HTML-element name is allowed, a non-Base nested class gets no helper, helpers also work when the yielded root is passed to another component; the `render_as_child` merge table: child wins, PLAIN class join slot-then-child incl. a conflicting pair such as `rounded-md` + `rounded-full` that must BOTH survive, `data-action` concat child-first, style merge, only-slot and only-child props; first-use thread safety of the caches); `ruby .claude/scripts/shadcn/cn_differential.rb` passes (the port's `cn` = Ruby `tailwind_merge`, the oracle's = JS `twMerge` 3.x; they must agree on every merge of real shadcn class strings); the `_harness` self-test uses it.

## `_icons`
What exists: `Chadcn::Icon` rendering the exact lucide SVG (same version as `lucide-react` in the catalog `package.json`): `viewBox 0 0 24 24`, `fill none`, `stroke currentColor`, `stroke-width 2`, `stroke-linecap/linejoin round`, `aria-hidden`, `class` passthrough, no default size class (like lucide-react, which renders width/height 24 only; shadcn components size their icons via parent selectors such as `[&_svg:not([class*='size-'])]:size-4`). The paths live in the generated catalog `lib/chadcn/icons/catalog.rb` (excluded from RuboCop), built from exactly the icon names the manifests, scenarios and oracle imports use, so nothing is hand-drawn.
The catalog is generated, never hand-edited: `ruby .claude/scripts/shadcn/icons_sync.rb` (union of manifest icons, scenario `<icon:name>` and oracle lucide imports, harness name resolution); `--check` exits 1 when a scenario needs an icon the catalog lacks.
Acceptance: `icons_sync.rb --check` passes; for every icon name in the union, the Phlex SVG `outerHTML` equals the React `lucide-react` render (compare normalized attributes + path `d`; `test/chadcn/icon_test.rb` and the `_harness` icon case).

## `_harness`
What exists, both sides of the parity contract (`references/parity-gates.md`):
1. React: `dev/react-shadcn-catalog/src/parity/Harness.tsx` (hash router: `#/parity/:component/:scenario`) that loads `dev/port/scenarios/:component.json` (Vite alias `@scenarios`, `server.fs.allow` to the repo root) and renders `tree` using `import.meta.glob("../components/ui/*.tsx")`. `{ "c": "DialogTrigger", "props": { "asChild": true } }` renders the real component; a node whose `c` starts with `_` (`_a`, `_div`...) renders the raw element with `props` as attributes (identical rule in the Phlex `TreeRenderer`); children strings stay text; `<icon:name>` renders the lucide icon. Body classes `bg-background text-foreground`; page padding fixed (e.g. `p-8`) and identical to the Phlex layout.
2. Phlex: the dummy app's route `get "design-system/parity/:component/:scenario"` -> `ParityScenariosController` -> `ShadcnParity::Page` -> `ShadcnParity::TreeRenderer` (`dev/parity`), which maps `c` to `Chadcn::<Root>[::<Part>]` per api-mapping (`className`->`class`, camelCase->snake_case, `asChild` rule, `<icon:x>`), no layout chrome except the same body/padding. Unknown component or any render error -> an element with the attribute `data-parity-error` containing the message (and a non-2xx status); the runner reports `PARITY_ERROR` / `HTTP_STATUS` / `EMPTY_RENDER`, so a broken page can never compare equal to another broken page.
3. Both layouts load the same fonts and set `html{font-size:16px}`; the Phlex page includes the compiled Tailwind (theme files), Stimulus and the gem's importmap pins.
3b. **DX mode.** `TreeRenderer` has two modes selected by `?dx=helpers` (default: explicit nested classes). In helper mode a node whose component is a nested part of the enclosing compound root is rendered through the YIELDED ROOT (`render Root.new(**props) do |root| ... root.public_send(helper, **props) { children } end`, helper names from `spec_helpers.rb`'s rule); everything else (non-compound components, raw `_` elements) is unchanged. `parity_run.mjs --dx helpers` appends the flag to the Phlex URL only, so the SAME scenario tree is compared with React through both paths.
4. Dev servers are managed by `.claude/scripts/shadcn/servers.rb start|status|stop` (free ports, `dev/tmp/shadcn-port/servers.json`; do not add a second launcher); `bin/test-js` and `bin/demo` use the same launcher.
5. Self-test scenario `dev/port/scenarios/_harness.json` with 3 hand-written cases (plain div tree, nested, `<icon:x>`), which must produce zero diffs through `parity_run.mjs --component _harness` using stub components so the harness is proven before any real component uses it.
Acceptance: `node parity_run.mjs --component _harness` exits 0 and a deliberately broken probe (extra class on the Phlex side) exits 1 (run both once and record in `tmp/shadcn-port/_harness/selftest.json`); `servers.rb status` exits 0 while the servers run; the dummy app's Minitest suite (parity and catalog tests, run by `bin/check`) passes.

## `_primitives`
What exists: every module in `.ai/skills/radix-stimulus/references/primitives.md` under `app/javascript/chadcn/primitives/`, each with a harness page and a scenario file `_primitives-<name>.json` comparing it with the raw Radix primitive in React (`dev/react-shadcn-catalog/src/parity/primitives/<name>.tsx` using `radix-ui` directly, same markup), pinned in the gem's `config/importmap.rb` (`pin_all_from File.expand_path("../app/javascript/chadcn", __dir__), under: "chadcn"`; the engine adds that file to a consuming app's importmap, the esbuild path copies the files). floating-ui is vendored in `vendor/javascript` and pinned in the gem's importmap at the catalog's version; to re-pin, download the `@floating-ui/dom` release that matches the catalog, replace the files in `vendor/javascript` and the version comments in `config/importmap.rb`; `house_check.rb` fails `G5_FLOATING_UI_VERSION` on a mismatch. Split by family when running builders in parallel: `overlay` (presence, portal, template_mount, dismissable_layer, focus_scope, focus_guards, hide_others, scroll_lock), `floating` (positioner, hover_intent, submenu_grace), `selection` (roving_focus, typeahead, collection, direction, ids), `forms` (form_bubble_input, pointer_capture).
Acceptance: all `_primitives-*` scenarios pass G2/G3; `test/javascript/primitive_*.test.mjs` pass under `bin/test-js`.
